# Adapt go-gibo-ingestion's kifu JSONL into training data, re-validate GAB on real human games

Priority: high
State: done

## Problem

`docs/board-specification.md` §7/§8's entire GAB validation runs on
self-play data generated by a randomly-initialized, never-trained net
(§8d/§8e's own stated caveat, line 637: "every self-play game in this
doc is generated by a randomly-initialized... net"). §8d/§8e's finding
was that more volume from that generator doesn't help — the generator
itself, not `gab_gen_size` or data size, is the ceiling. `003` attacks
this by bootstrapping a better generator over several self-play
generations; this spec attacks it more directly by removing the weak
generator entirely and training on real human games instead.

**This spec was re-scoped after it was first drafted** (see Decision
Log #1-#3). Originally it owned fetching and SGF-parsing directly
inside `go-style-engine/data/`. That work has since moved to a
sibling repo, `~/repositories/individual/go-gibo-ingestion`
(decoupling ingestion from the model repo, the same reasoning
`nem-forecast-orchestration` is split from `nem-forecast`) — that repo
now owns `fetch.py` (downloads CWI's 9x9 archive) and `ingest.py`
(parses SGF into normalized `data/parsed/9x9.jsonl`, one JSON record
per game). This spec's remaining job is narrower: adapt that JSONL
into this project's `train.py`-compatible `.npz` format, and run the
re-validation.

**A second, more consequential re-scope**: `go-gibo-ingestion`'s own
end-to-end run against the real archive found that **419 of the
517 games (81%) are `Minigo` — AI self-play by the Minigo project
(an AlphaGo-Zero-style open-source bot), not human kifu.** Only 80
games, across categories `NHK`/`ProPairgo`/`Misc`/`Go_Seigen`, are
actually human-played. This spec's whole premise is "real human signal
vs. a weak random-net generator," so it targets that 80-game
human-only subset by default (Decision Log #2) — a real, small dataset,
not the 517/419 numbers this spec's first draft assumed.

## Desired Behavior

1. **Prerequisite** (run in `go-gibo-ingestion`, not here):
   ```sh
   cd ~/repositories/individual/go-gibo-ingestion
   .venv/bin/python fetch.py
   .venv/bin/python ingest.py --input data/raw/9x9 --archive-name 9x9 \
     --output data/parsed/9x9.jsonl
   ```
   Produces `data/parsed/9x9.jsonl` — see that repo's README for the
   exact record schema (`game_id`, `category`, `board_size`, `komi`,
   `players`, `result`, `moves: [{color, pass, col, row}]`,
   `has_variations`).

2. **New adapter script**
   (`go-style-engine/data/kifu_to_experience.py`): reads a
   `9x9.jsonl` path (default:
   `../../go-gibo-ingestion/data/parsed/9x9.jsonl`, overridable via
   `--input`), filters to `category` in
   `{NHK, ProPairgo, Misc, Go_Seigen}` by default (`--categories` to
   override — e.g. to add `Minigo` back in for a future, explicitly
   different experiment; see Non-Goals), and for each remaining game:
   - Replays its `moves` through `engine/goboard.GameState`
     (`BoardSpec(board_size=9, ...)`, matching §7/§8's board size —
     `go-gibo-ingestion` already only emits 9x9 games). Map each
     move's 0-indexed `(col, row)` into this engine's 1-indexed
     `Point(row, col)` convention as `Point(row=row+1, col=col+1)` —
     the two repos deliberately use different coordinate conventions
     (see that repo's `sgf_reader.py` docstring), so this mapping is
     the seam between them, not a bug to "fix" on either side.
   - Encodes the state *before* each move via `TokenEncoder`, exactly
     as `selfplay.py`/`engine/mcts.py` already do.
   - Policy target: one-hot at `encoder.encode_move(move)` (not an
     MCTS visit distribution — see Edge Cases).
   - Value target: `+1`/`-1` from the mover's perspective, from the
     JSONL's already-parsed `result.winner` (no `RE[]` re-parsing
     needed here — `go-gibo-ingestion` already did that and already
     excluded draws/void/unparseable results upstream).
   - Writes `game_*.npz` shards in the exact format
     `engine/experience.py`/`selfplay.py` already produce (`states`,
     `visit_counts`, `rewards`), so `train.py --experience <dir>`
     works unmodified.

3. **Re-run §7/§8's GAB comparison** on the resulting dataset: same
   configs as §8's settled comparison (`pos_mode` sweep, then
   `pos_mode=gab_absolute` at `gab_gen_size` in `{4,16,64}` per §8c/§8e's
   sweep grid), same early-stopping/val-split discipline (§8c), and
   record whether GAB's advantage over `absolute`/`relative` (found on
   random-net self-play) holds, strengthens, weakens, or reverses on
   real human game data.

## Non-Goals

- Not the 19x19/full-archive track — out of scope, per the original
  Decision Log #1 (kept below), for the same comparability reason.
- Not the `Minigo` (419-game AI self-play) or `computer` (18-game
  weak-engine) categories by default — see Decision Log #2. A future
  spec could explicitly compare human-only vs. human+Minigo results
  using the same `--categories` override this spec's adapter exposes,
  but that's a distinct experiment with its own write-up, not bundled
  here.
- Not a new architecture or `pos_mode` — reuses `TokenTransformerNet`
  exactly as-is; this is a data adapter + re-run, not a model change.
- Not a replacement for `003` — `003`'s iterative self-play question
  ("does a bootstrapped generator help") is still open and independent;
  this spec answers a different question ("does GAB's advantage
  survive real human data") and either could turn out to matter more
  than the other.
- Do not modify `go-gibo-ingestion` as part of this spec — if its
  output schema needs to change, that's a change in that repo first,
  with this spec's adapter following.

## Environment

CPU-only. Requires `go-gibo-ingestion`'s `fetch.py`/`ingest.py` to
have been run first (see Desired Behavior #1 — cheap, ~2MB, under a
minute). No new dependencies beyond the existing venv — the adapter is
plain `json`/`numpy`, no SGF parsing here (that's fully owned by the
sibling repo now).

## Dependencies

Soft dependency on `go-gibo-ingestion` existing and having been run at
least once locally (not a Python package dependency — just a JSONL
file on disk at a known relative path). No other blockers.

## Edge Cases

- **One-hot vs. MCTS-visit-distribution policy target.** §7/§8's
  self-play data has soft MCTS visit-count targets; kifu data only has
  the single move actually played, so the target here is necessarily
  one-hot. This is a real, acknowledged difference in target
  *sharpness*, not a bug — note it explicitly in the write-up so a
  reader doesn't assume the two runs are apples-to-apples on target
  softness, only on the network/GAB comparison itself.
- **80 games is a small dataset** — smaller than this spec's first
  draft assumed (which wrongly treated the full 517/499 as usable).
  Expect noisier results than §7/§8's own runs; don't over-claim a
  "trend reversal" from what could just be small-sample noise (same
  caution §8b/§8e already apply to their own single-seed runs).
- **Coordinate mapping** (`go-gibo-ingestion`'s 0-indexed `(col, row)`
  → this engine's 1-indexed `Point(row, col)`): get this right and
  verify it, not just implement it — a transposition or off-by-one bug
  here would silently corrupt every training example. Spot-check a
  handful of converted games by hand (e.g. render the first few moves
  of a known game and compare against the original SGF) as part of
  implementing this, not just unit-test the mapping function in
  isolation.
- **Train/val split**: split by *game*, not by position (kept from the
  original Decision Log #3 below) — positions from the same game are
  highly correlated, and a position-level split would leak.

## Test Expectations

- `test_kifu_to_experience.py`: runs the adapter against a tiny
  synthetic fixture JSONL (2-3 records, matching
  `go-gibo-ingestion`'s real schema, including at least one pass move)
  and confirms the output `.npz` shards load correctly via
  `engine/experience.py`'s existing `load_shard`/combine path and that
  `train.py --experience <dir>` can consume them end-to-end (one
  epoch, no crash) without modifying `train.py`. Also test the
  `--categories` filter excludes/includes games correctly.
- `cd go-style-engine && .venv/bin/python -m pytest -q` — full suite
  passes.
- Manual/experiment step (not a pytest test): running
  `kifu_to_experience.py` against the real
  `go-gibo-ingestion/data/parsed/9x9.jsonl` and confirming the
  reported game/position counts are sane (80 games in, by default),
  plus the hand-verified coordinate spot-check above.

## Known Risks

Realized, not just anticipated: the result is a genuine negative
finding, not the noisy-but-directional read this spec's risk
assessment expected. §8f found the value head fails to learn *at all*
(train loss flat at the constant-predictor baseline, not just a val
gap) on real human data, in every config tried — a flatter, more
consistent non-result than "medium-high risk of noise" implied, which
if anything argues the result is real rather than sampling artifact
(see §8f's own discussion of why). The coordinate-mapping risk this
section originally flagged did not materialize — verified clean by
hand against real data, see Acceptance Criteria.

**Update: §8f's headline finding above was itself wrong — see
Decision Log #6 and `docs/board-specification.md` §8g.** It was an
`--early-stopping-patience` artifact, not a real learning failure.
Left here unedited as the record of what this spec's risk assessment
got right (a genuine, reproducible result) and wrong (the wrong causal
explanation for it) — see Decision Log #6 for what actually happened.

## Decision Log

| # | Proposed | Status | Why |
|---|---|---|---|
| 1 | Scope to 9x9 only (517-game archive) vs. 19x19 (full 96,058-game archive) vs. both as separate tracks. | **Accepted: 9x9 only** | Direct comparability to every existing §7/§8 number (all measured at 9x9/81 tokens) matters more than dataset size for this specific question — a 19x19 run would be a new baseline, not a re-validation. Decided with the repo owner before this spec was first written. |
| 2 | After `go-gibo-ingestion`'s real end-to-end run showed 419/517 games are `Minigo` AI self-play, not human: include Minigo as part of the training pool anyway (since it's a genuinely strong generator, unlike this project's own random-net one) vs. human-only (80 games) vs. both as separate tagged tracks. | **Accepted: human-only, 80 games** | The spec's entire premise is testing real *human* signal against a random-net self-play baseline — mixing in a different (if stronger) AI generator would muddy exactly the comparison this spec exists to make. `category` is preserved in `go-gibo-ingestion`'s output specifically so a future spec can revisit Minigo-inclusive or Minigo-only variants without re-scoping this one. |
| 3 | Position-level train/val split (simpler to implement) vs. game-level split. | **Accepted: game-level** | Positions within one game are highly correlated (same board, adjacent history windows); a position-level split would leak information between train and val, understating true val loss the same way §8b's "wrong fixed epoch" problem understated overfitting — avoid a second, avoidable measurement bias. |
| 4 | Own fetching and SGF parsing directly inside `go-style-engine/data/` (this spec's original scope) vs. split that work into a separate `go-gibo-ingestion` repo. | **Accepted: split into go-gibo-ingestion** | Ingestion concerns (fetching, parsing, validating source data) don't belong in a model-training repo — the same reasoning `nem-forecast-orchestration` is split from `nem-forecast`. Scoped deliberately light (plain fetch/parse scripts, no Dagster/dbt/DuckDB orchestrator) since there's one static source today, not several live feeds needing scheduling; escalate the tooling only if that changes. This spec's `Likely Files`/`Desired Behavior` were rewritten to match — the SGF-parsing work originally planned here now lives in that repo instead. |
| 5 | Preserve player-identity metadata (`PB`/`PW`/`BR`/`WR`) for future personality-conditioning use, vs. drop it since nothing currently consumes it. | **Accepted: preserved upstream, not threaded through here** | `go-gibo-ingestion`'s JSONL already carries full `players` metadata per game (near-zero cost to keep at that layer); this spec's `.npz` output format has no metadata slot (matching `train.py`'s existing format exactly, unmodified) — a future style-conditioning spec that needs to correlate positions back to specific players can re-join against `go-gibo-ingestion`'s JSONL by `game_id` rather than needing it threaded through the training format now on spec. |
| 6 | §8f's "value head does not learn on real human data" finding stood as written vs. investigating the one anomaly that didn't fit (`pos_mode='both'` uniquely broke through in a follow-up 13x13 extension of this same spec) before accepting it as final. | **Investigated — finding corrected, not confirmed** | Tracing why `both` alone succeeded led to the real cause: `--early-stopping-patience 3` (settled on self-play data in §8c) tracks *combined* policy+value loss, so a config whose policy loss keeps improving longer (as `both`'s did) gets more epochs of cover before patience exhausts than one whose policy plateaus early (`absolute`) or diverges (`gab_absolute`) — nothing to do with whether the value head *can* learn. Re-running `absolute` with a much longer patience budget confirmed it breaks through too, at both 9x9 (this spec's original dataset) and 13x13 — see `docs/board-specification.md` §8g for the full trace and the corrected conclusion.
